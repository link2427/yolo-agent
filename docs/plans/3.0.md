# yolo-agent 3.0

Status: **plan, not built.** Written 2026-11-09. Replaces the earlier
`REVAMP.md`, `AGENT-VERSIONS.md` and `PACKAGE-MIRROR.md` drafts. The one finding
kept from them is the pi image-input bug (section 9).

## 1. Requirements

| Requirement | Source |
| --- | --- |
| Fully self-contained release: no network at runtime, everything baked at build time | owner |
| Fits on one disc, or a few | owner |
| code-server (VS Code) and a browser terminal stay | owner |
| Easy to get files in and out of the container | owner |
| Docker Compose only; no launcher scripts | owner |
| No logins on the LAN services | owner |
| Static lab defaults: vLLM `192.168.1.101:8000`, Gitea `192.168.1.27:3000`, git `YOLO Agent <yoloagent@gmail.com>` | owner |

| An always-on agent that does work unattended (PR review first) | owner |

## 2. Two stacks

```
 workstation stack  (compose.yaml, one per person: docker compose -p alice up -d)
 ┌──────────────────────────────────────────────────────────────────────┐
 │ home      :80    start page: big buttons to everything below          │
 │ code      :8080  code-server + Cline + Kilo Code chat panels          │
 │ term      :7681  ttyd + tmux                                          │
 │ chat      :4096  opencode web (full agent: tools, edits, terminal)    │
 │ files     :8081  File Browser on /workspace                           │
 └──────────────────────────────────────────────────────────────────────┘
          │ OpenAI / Anthropic API                │ git, fleet, skills
          ▼                                       ▼
 lab stack  (compose.lab.yaml, once, on a lab server)
 ┌──────────────────────────────────────────────────────────────────────┐
 │ gateway   :4000  LiteLLM: model aliases, per-person keys, request log │
 │ monitor   :3100  custom vLLM telemetry UI + collector + storage       │
 │ bot              always-on agent: Gitea PR review, scheduled jobs     │
 └──────────────────────────────────────────────────────────────────────┘
          │                                       │
          ▼                                       ▼
   SEC09 vLLM 192.168.1.101:8000          Gitea 192.168.1.27:3000
```

Every workstation service runs from the same image with a different command.
Compose restart policies supervise them; the bash restart loop goes away.

## 3. Image: one Dockerfile, layered tiers

```
images/agent/Dockerfile
  os        Debian 12, apt userland, agent user           (changes rarely)
  core      Python 3.11 env, Node 22, code-server, ttyd, agents, tools
  cpp       core + C/C++/Fortran + mingw-w64             FROM core
  full      cpp + reverse-engineering tools               FROM cpp
```

- Each tier is `FROM` the previous one, so `cpp` and `full` are deltas.
- Layers are ordered from rarely to often changing: OS, toolchains, Python,
  Node, code-server, agents, config.
- Copy everything with `--chown`; no recursive `chown` after a copy. The 2.x
  Dockerfile duplicates the opencode and pi trees this way.
- Tags: `yolo-agent:3.0.0-core`, `-cpp`, `-full`.

**Measure before promising disc sizes.** First task of the build: record the
compressed size of each tier and of the combined archive.

## 4. Release and distribution

- One archive holds all tags: `docker save core cpp full | zstd -19 --long`.
  `docker save` writes shared layers once.
- Optional split into 4.3 GiB parts for DVD, with `SHA256SUMS` and a
  reassembly note.
- Bundle contents: the archive, `compose.yaml`, `compose.lab.yaml`,
  `.env.example`, `install.ps1`, `install.sh`, docs, checksums.
- **Gitea container registry.** Load once on the lab server, push to
  `192.168.1.27:3000`, and every host runs `docker compose pull`. Later
  update discs then only need the layers that changed. `docker load` from disc
  stays the fallback.
- Lab images (gateway, monitor, bot) ship in the same release.

## 5. Configuration

- Lab values are baked as defaults; `.env` overrides them.
- **The Gitea token is never in the repo or the image.** It goes in the
  lab-side `.env` or is stored once in the home volume by `yolo login`.
- The entrypoint writes agent and git config on every start. `.bashrc` no
  longer does it, so services that never open a shell are configured too.
- `/v1/models` is read at start, and every served model is written into each
  agent's model picker.

## 6. Files in and out

- code-server: drag and drop to upload, right-click to download (unchanged).
- File Browser service for bulk upload, download and zip.
- `/workspace` is a bind mount of a WSL ext4 path such as `~/yolo/alice`,
  never `/mnt/c`. It stays fast and is reachable from Windows Explorer at
  `\\wsl.localhost\<distro>\home\<user>\yolo\alice`.

## 7. Agents

Terminal agents, all aimed at the gateway (or SEC09 directly):

| Agent | Form | API | Notes |
| --- | --- | --- | --- |
| opencode | binary | OpenAI | also serves the web UI |
| pi | binary | OpenAI | fix image input (section 9) |
| Qwen Code | npm | OpenAI | built for Qwen; strongest candidate |
| Crush | Go binary | OpenAI | FSL-1.1-MIT licence |
| Goose | Rust binary | OpenAI | no web UI any more |
| Kilo CLI | npm | OpenAI | opencode-based |
| Codex | static binary | Responses only | experimental: needs vLLM `/v1/responses` |
| Claude Code | binary | Anthropic | experimental: vLLM `/v1/messages` (vLLM >= 0.11.1) |
| Aider | pip | OpenAI | optional; no skills |

DeepSeek Harness is removed.

Web and GUI agents:

- **opencode web** on :4096. It is the full agent, including the terminal.
  Official builds embed the UI; without the embedded bundle it proxies to
  `app.opencode.ai`, which fails offline. Never set
  `OPENCODE_DISABLE_EMBEDDED_WEB_UI`. Set `OPENCODE_DISABLE_AUTOUPDATE=1`,
  `OPENCODE_DISABLE_MODELS_FETCH=1`, `OPENCODE_DISABLE_LSP_DOWNLOAD=1`.
- **Cline** and **Kilo Code** as preinstalled code-server extensions, so people
  get a chat panel with diffs and apply/reject buttons and never need the
  terminal. Roo Code is archived upstream and is left out.
- **Start page** on :80 with plain buttons: Chat, VS Code, Files, Terminal, plus
  the current model and whether SEC09 is up.

Every agent gets its telemetry, update checks and remote model catalogues
turned off. Each is tested with the network disabled.

## 8. Always-on bot

Runs from the agent image, so it costs no extra disc space.

- **PR review:** a small webhook receiver takes Gitea pull-request events,
  checks the branch out, runs a headless agent (`opencode run`, or `qwen -p`)
  with a review prompt and the repo's own build and test commands, and posts
  the review through the Gitea API. Unlike a diff-only reviewer, it can build
  and run the tests.
- **Scheduled jobs:** a jobs file in the fleet repo (nightly dependency audit,
  stale-PR summary, and so on), run on a cron schedule.
- **Comment trigger:** `@yolo` in a PR comment runs the agent on that request.
- Hermes Agent (Nous Research, MIT) is the alternative if a chat and web UI
  for the bot itself is wanted. It is a heavy Python stack with plugins that
  reach the network, so it is evaluated after the bot above works.

## 9. Fleet management

- **Fleet repo** in Gitea, `yolo/fleet`: default model, agent settings, a
  shared `AGENTS.md`, the skills index, bot jobs. Containers pull it on start
  and on `yolo sync`. Changing everyone's model is one commit.
- **Gateway** (LiteLLM): agents only use aliases such as `yolo-default` and
  `yolo-fast`. Remapping an alias moves everyone without touching containers.
  It also gives per-person keys, usage, and a per-request log for the monitor.
- **pi image input:** `configure-agents.sh` writes no `input` field, and pi
  defaults to `["text"]`, so images never reach the model. Write
  `"input": ["text", "image"]` for vision models.

## 10. Skills

One library, nothing loaded by default.

- **Library:** skills live in a Gitea repo, `yolo/skills`, each as a
  `SKILL.md` folder. A snapshot is baked into the image at
  `/opt/yolo/skills` for first boot.
- **Enabled set:** only enabled skills are linked into the folders agents
  scan. The default enabled set is a handful of core skills.
- **CLI:**
  - `yolo skills list | search <text> | show <name>`
  - `yolo skills enable <name> [--project] [--agent <name>]`
  - `yolo skills disable <name>`
  - `yolo skills pack enable cpp|reverse|web` (named bundles)
- **Linking:** one canonical folder per scope, `~/.agents/skills` (user) or
  `.agents/skills` (project), plus symlinks for agents that scan their own
  folder (pi, opencode, Qwen Code, Claude Code). The linking table is per agent
  and tested.
- **Fleet:** the fleet repo can enable a skill for everyone, or for one person.

## 11. Monitoring

A custom UI that has to look excellent. It is its own image, built from this
repo, not a separate repository.

- **Data:**
  - vLLM `/metrics`: throughput, time to first token, queue depth, KV-cache
    use, preemptions, every 2 to 5 s.
  - Gateway request log: person, agent, model, tokens, latency, errors.
  - Optional collector on SEC09 for GPU power, temperature, memory and
    utilisation.
- **Storage:** DuckDB. Full detail kept for a short window, rolled up to
  minutes and hours, older data archived as Parquet. One file to back up.
- **UI:**
  - a live view of SEC09 with animated live figures
  - a timeline that marks model swaps and restarts
  - usage by person and agent
  - a searchable request explorer
  - light and dark themes
  - designed by hand, not from a chart template
- Also feeds the start page's "is SEC09 up" indicator.

## 12. Local testing

SEC09 and Gitea are not reachable from the build machine. Tests use:

- a llama.cpp server with a small Qwen GGUF as a stand-in model, so every agent
  can really call tools against an OpenAI-compatible (and, for Claude Code,
  Anthropic-compatible through the gateway) endpoint;
- a throwaway Gitea container for the bot, fleet sync and skills;
- `--network none` runs of every service, to prove nothing reaches the
  internet;
- a BuildKit builder limited to 16 CPUs for all builds.

A last check against SEC09 itself happens in the lab.

## 13. Build order

1. Image tiers, compose, entrypoint config, defaults, size measurements.
2. Agents: Qwen Code, Crush, Goose, Kilo CLI, then Codex and Claude Code as
   experimental. Fix pi image input.
3. Web surfaces: opencode web, Cline and Kilo Code in code-server, File
   Browser, start page.
4. Skills CLI and library.
5. Lab stack: gateway and fleet repo.
6. Monitor.
7. Bot: PR review, then scheduled jobs.
8. Release packaging and the Gitea-registry flow.
